# Claude Code / Codex tooling inventory and smoke tests

Audit: October 11, 2026. Repository: Vote4U. Companion: [agent development guide](../ios/AGENT_DEVELOPMENT_GUIDE.md).

## Scope and evidence

The repository contains agent instructions and project documentation, but no checked-in `.claude/`, `.codex/`, `.agents/`, or `.mcp.json` tooling directories/config. This audit therefore inspected the user installations used with this repo. It read skill files and plugin manifests, extracted only allowlisted configuration fields, and checked the currently exposed tool names. Authentication stores, histories, environment secret values and MCP authentication headers are excluded.

Found **255 skill entry points**, **26 plugin manifests**, and **23 MCP definitions**. These are entries, not unique capabilities: aliases, host ports, older nested copies and plugin copies are retained individually. A cache entry or enabled setting does not prove successful loading, login or an available tool. Marketplace catalog entries and trash are not installed plugins and are excluded. Runtime tools can differ from local config.

**Checks actually run:** Xcode MCP workspace/scheme/target discovery passed (`Vote4U` shared active scheme; app, unit, UI and widget targets). XcodeBuildMCP `session_show_defaults` passed with unset defaults; `list_sims` returned iOS 17.5 and 27.0. Xcode 27.0 / Swift 6.4 CLI version checks passed. Shell `simctl` discovery failed under sandbox service/log access restrictions; MCP discovery succeeded. Bun, Claude, Codex and gh are on PATH; `asc` and `ettrace` were not found on PATH. No app test/build, profiling/bridge integration, Claude plugin invocation, external-service login, write operation or release action was performed for this audit.

All smoke tests below are **proposed, not run**, except the discovery checks above. Read each installed SKILL.md before use; the short purpose is its declared description, not a promise that it works.

## Test protocols

For any skill: (1) confirm the named entry is advertised by the host; (2) read it and needed references; (3) use a disposable/synthetic fixture with a known expected result; (4) verify its actual output or behavior; (5) record failure/skip/unavailable separately. Do not install, authenticate, spend, publish, send messages, delegate or alter the real app simply to test availability.

| Protocol | Procedure and pass criteria |
| --- | --- |
| N — native | Follow the specific fixture check below, build compatible Swift, then use screenshots/behavior assertions and `scripts/test-ios.sh` for acceptance. |
| M — MCP | Discover actual tool schema, call read-only discovery, verify project/device; use a requested QA action only when prerequisites are established. |
| P — profiling | Use one controlled flow and matching build/device; preserve traces/memgraphs and compare evidence; remove temporary instrumentation. |
| D — device bridge | Read/install prerequisites on a disposable synthetic app first; verify debug-only isolation, redacted state and no distribution linkage. |
| A — store/marketing | Use supplied listing/source fixture offline; detect seeded issue and corrected result. Authentication or campaign actions are separate. |
| R — review/research | Use a known bug/diff/question with bounded read-only scope; require grounded findings/citations. External-agent runs only when requested. |
| L — local guidance | Use a small supplied synthetic input, check declared deliverable against input/source, verify references/commands and no unintended writes. |
| B — browser/UI | Discover correct surface, inspect hierarchy/screenshot, run authorized fixture interaction, inspect result; web QA is not native QA. |
| F — artifact | Use synthetic requested file; open/render and inspect pages/layout/data/formulas; no connected writes as availability check. |
| C — connector | Read-only list/search/inspect in authorized account; confirm identity/permissions; no messages, events, publishing or file mutation. |
| H — workflow/config | Inspect prerequisites/dry-run in disposable fixture; verify bounded intended diff; never execute destructive/production actions to test guards. |
| G — generated visual | Only if requested: generate small fixture asset, open/inspect against prompt; no billable external provider setup inferred. |

## Runtime-provided MCP/tool surfaces

The session exposes `xcode`, `xcodebuild`, `node_repl`, `codex_tui` and `codex_apps` through the tool orchestrator, plus `cua_repl` directly. `codex_apps` is an account-connector gateway, not a checked-in repo MCP config. `codex_tui` is host task management, not proof the plugin server named `codex_app` has the same API. Built-in shell, web, clock and image tools are capabilities, not repo-installed MCP servers.

XcodeBuildMCP exposed names at audit: `session_show_defaults`, `session_set_defaults`, `session_clear_defaults`, `session_use_defaults_profile`, `discover_projs`, `list_schemes`, `show_build_settings`, `list_sims`, `boot_sim`, `open_sim`, `build_sim`, `build_run_sim`, `test_sim`, `clean`, `get_sim_app_path`, `get_app_bundle_id`, `install_app_sim`, `launch_app_sim`, `stop_app_sim`, `screenshot`, `snapshot_ui`, `record_sim_video`, `get_coverage_report`, `get_file_coverage`. The plugin skill’s older `describe_ui`/tap/gesture/log/LLDB names are not exposed by this active namespace; inspect the current server rather than calling assumed tools.

Xcode bridge includes discovery/settings/file operations, documentation search, builds/run/tests, previews/snippets, debugger/console, device interactions, localization and field crash/performance tools. Read the actual schema for each call. Connection discovery is tested; individual mutating tools and field-data authentication are not.

## Re-audit on another machine

Inspect repo instructions/config first, then `~/.claude/skills`, installed plugin registry/settings and project MCP config, then `~/.codex/skills`, `config.toml`, plugin manifests and current session discovery. Follow symlinks and identify duplicate versions, but do not count entire marketplace catalogs, trash, vendored dependencies or test fixtures as installed skills. Extract only names/status/command/package/env **names**, never secrets or auth headers. Read the relevant skill’s references/scripts before applying it.

Use the proposed fixture test for each selected tool and record `discovered`, `loaded`, `connected`, `authenticated`, `fixture passed`, or `unavailable` separately. Do not call an enabled config a passed test. Preserve the project-specific test runner and owner merge/release boundary described in the [guide](../ios/AGENT_DEVELOPMENT_GUIDE.md).
